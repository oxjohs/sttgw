# 2차 작업계획서

## 1. 목적

본 문서는 `sttgw` 프로젝트의 2차 작업 범위와 구현 원칙을 정의한다.  
2차의 핵심 목표는 1차에서 만든 패키지 골격 위에 내부 서비스 흐름과 영속성 기초를 추가하여, 문서상 핵심 모듈이 실제 코드 구조로 이어지도록 만드는 것이다.

이번 단계에서 다루는 핵심 영역은 아래와 같다.

- `domain`
- `repository`
- `session`
- `audio`
- `sip`
- `rtp`
- `stt`

## 2. 단일 진실 기준

2차 작업은 아래 문서를 기준으로 한다.

- `AGENTS.md`
- `docs/ARCHITECTURE.md`
- `docs/CONVENTIONS.md`
- `docs/SCHEMA.md`
- `docs/DEPLOYMENT.md`
- `docs/1차-작업계획서.md`

문서와 코드가 충돌하면 문서를 우선한다.

## 3. 현재 상태

- 1차 작업을 통해 `common`, `config`, `session`, `audio`, `sip`, `rtp`, `stt` 패키지의 기초 타입이 생성되었다.
- 아직 실제 동작 서비스인 `SipParser`, `CallSessionManager`, `RtpDecoder`, `WavFileWriter`, `AudioFileService`, `SttAdapterFactory` 는 없다.
- `domain`, `repository` 패키지도 아직 없다.
- 따라서 현재 구조는 읽을 수는 있으나, SIP 입력부터 세션 관리와 오디오 파일 생성까지 이어지는 내부 흐름은 아직 비어 있다.

## 4. 2차 작업 목표

이번 2차 작업의 세부 목표는 아래와 같다.

1. 데이터베이스 스키마 문서를 기준으로 엔티티와 리포지토리를 만든다.
2. SIP 파싱 → 세션 생성/종료 → RTP PCM 누적 → WAV 파일 저장의 내부 흐름을 코드로 연결한다.
3. STT 어댑터 조회를 담당하는 최소 팩토리 계층을 추가한다.
4. 외부 인프라 의존성 추가 없이 구현 가능한 범위까지만 진행한다.

## 5. 작업 범위

### 5.1 domain / repository

목적:

- `SCHEMA.md` 기준의 JPA 엔티티와 조회 인터페이스를 마련한다.

생성 대상:

- `domain/CallRecord`
- `domain/SttTranscript`
- `domain/SttVendorConfig`
- `repository/CallRecordRepository`
- `repository/SttTranscriptRepository`
- `repository/SttVendorConfigRepository`

구현 원칙:

- 테이블명, 컬럼명, 기본값, enum 매핑은 문서 기준을 따른다.
- `SttVendorConfig.defaultConfig()` 를 제공한다.

### 5.2 session

목적:

- SIP 이벤트를 받아 세션을 생성/종료/취소하고, RTP 오디오를 세션별로 누적한다.

생성 대상:

- `session/CallSessionManager`

수정 대상:

- `session/CallSession`

구현 원칙:

- 세션 저장소는 `ConcurrentHashMap` 기반으로 유지한다.
- 미디어 포트와 `Call-ID` 매핑을 별도로 둔다.
- 세션 종료 시 `CallRecordRepository` 를 통해 기본 통화 이력을 저장한다.

주의:

- 오디오 파일 저장은 비동기이므로 종료 시점에 `rxAudioPath`, `txAudioPath` 가 아직 비어 있을 수 있다.
- 이 한계는 이번 단계에서 허용하고, 후속 단계에서 보완한다.

### 5.3 audio

목적:

- 누적된 PCM 데이터를 WAV 파일로 만들고, 세션 종료 후 비동기로 파일을 생성한다.

생성 대상:

- `audio/WavFileWriter`
- `audio/AudioFileService`

구현 원칙:

- `AudioFileService` 는 `SessionEventListener` 구현체로 동작한다.
- 쓰기 스레드는 별도 executor 로 분리한다.
- 날짜 기반 디렉토리 구조는 문서 기준 `yyyy/MM/dd` 를 사용한다.

### 5.4 sip

목적:

- SIP 텍스트와 SDP 정보를 파싱하여 세션 관리자에게 이벤트를 전달한다.

생성 대상:

- `sip/SipParser`

수정 대상:

- `sip/SipMessage`
- `sip/SipMethodType`

구현 원칙:

- `INVITE`, `BYE`, `CANCEL` 을 우선 처리한다.
- `Call-ID`, `From`, `To`, `tag`, `m=audio`, `c=IN IP4` 를 우선 추출한다.

### 5.5 rtp

목적:

- RTP 패킷을 해석하고 G.711 코덱을 PCM 으로 변환한 뒤 세션 관리자에 전달한다.

생성 대상:

- `rtp/RtpDecoder`

구현 원칙:

- `payloadType=8` 은 A-law, `payloadType=0` 은 u-law 로 처리한다.
- 지원하지 않는 payload type 은 로그 후 무시한다.

### 5.6 stt

목적:

- 현재 등록된 STT 어댑터 목록에서 사용 가능한 어댑터를 조회하는 최소 팩토리를 제공한다.

생성 대상:

- `stt/SttAdapterFactory`

구현 원칙:

- `List<SttAdapter>` 기반으로 조회한다.
- 설정 기본 벤더와 사용 가능 여부를 반영한다.
- 실제 벤더 구현체는 이번 단계에서 만들지 않는다.

## 6. 제외 범위

이번 2차에서는 아래 범위를 제외한다.

- `capture` 패키지
- `websocket` 패키지
- `dashboard` 패키지
- `api` 패키지
- `stt/google` 구현
- `schema.sql`, `data.sql` 작성
- 실제 패킷 캡처 연동
- 실제 Google STT 호출

## 7. 상세 작업 순서

### 7.1 문서 작업

1. 본 계획서를 작성한다.
2. 문서만 먼저 커밋한다.
3. GitHub 원격에 푸시한다.

### 7.2 영속성 및 세션/오디오 기반

1. `domain` 엔티티를 추가한다.
2. `repository` 인터페이스를 추가한다.
3. `CallSession` 을 보강한다.
4. `CallSessionManager` 를 추가한다.
5. `WavFileWriter`, `AudioFileService` 를 추가한다.
6. 해당 단위를 커밋하고 푸시한다.

### 7.3 SIP / RTP / STT 서비스

1. `SipMessage`, `SipMethodType` 를 보강한다.
2. `SipParser` 를 추가한다.
3. `RtpDecoder` 를 추가한다.
4. `SttAdapterFactory` 를 추가한다.
5. 해당 단위를 커밋하고 푸시한다.

## 8. 예상 리스크

### 8.1 오디오 경로 저장 시점

- `AudioFileService` 는 비동기로 동작하므로 `CallRecord` 저장 시점과 파일 생성 시점이 다를 수 있다.
- 결과적으로 `CallRecord.rxAudioPath`, `CallRecord.txAudioPath` 는 초기에 null 로 저장될 수 있다.

### 8.2 테스트 미실행

- 이번 단계에서도 빌드/테스트를 수행하지 않으므로 컴파일 성공을 보장하지 않는다.
- 따라서 구현은 문서/의존성 기준으로 가장 보수적으로 유지해야 한다.

### 8.3 SIP 파싱 범위 제한

- `SipParser` 는 모든 SIP 변형 메시지를 완벽히 커버하지 않는다.
- 2차에서는 문서에 나온 핵심 헤더와 SDP 구조에 집중한다.

## 9. 완료 기준

아래 조건을 만족하면 2차 작업을 완료로 본다.

1. `docs/2차-작업계획서.md` 가 작성되어 있다.
2. `domain`, `repository` 패키지가 생성되어 있다.
3. `CallSessionManager`, `SipParser`, `RtpDecoder`, `WavFileWriter`, `AudioFileService`, `SttAdapterFactory` 가 존재한다.
4. SIP 입력과 RTP 입력을 내부 세션 흐름으로 연결하는 코드가 존재한다.
5. 작업 단위별 한국어 커밋 메시지로 커밋되어 있다.
6. 각 의미 있는 작업단위 종료 후 GitHub 원격에 푸시되어 있다.
