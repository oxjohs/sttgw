# 1차 작업계획서

## 1. 목적

본 문서는 `sttgw` 프로젝트의 1차 골격 작업 범위와 구현 원칙을 정의한다.  
이번 단계의 목표는 실제 패킷 캡처나 Google STT 연동까지 한 번에 구현하는 것이 아니라, 문서 기준 아키텍처를 따르는 핵심 패키지와 타입을 먼저 안정적으로 세우는 것이다.

1차 작업 대상 패키지는 아래와 같다.

- `common`
- `config`
- `session`
- `audio`
- `sip`
- `rtp`
- `stt`

이번 단계에서는 외부 시스템 의존도가 높은 `capture`, `websocket`, `api`, `dashboard`, `repository`, `domain`, `stt/google` 구현은 제외한다.

## 2. 단일 진실 기준

1차 작업은 아래 문서를 기준으로 한다.

- `AGENTS.md`
- `docs/ARCHITECTURE.md`
- `docs/CONVENTIONS.md`
- `docs/SCHEMA.md`
- `docs/DEPLOYMENT.md`

구현 중 문서와 코드가 충돌하면 문서를 우선한다.

## 3. 현재 상태

- 현재 프로젝트는 Spring Boot 기본 스캐폴딩 상태다.
- 메인 애플리케이션 클래스와 기본 테스트만 존재한다.
- 목표 아키텍처에 필요한 패키지와 클래스 대부분이 아직 없다.
- `build.gradle` 에는 1차 골격 작업에 필요한 기본 Spring Boot, Lombok, Validation, JPA 의존성은 이미 포함되어 있다.
- `Pcap4J`, `Spring WebSocket`, `Google Cloud Speech` 의존성은 아직 없으므로 관련 구현은 이번 단계에서 직접 다루지 않는다.

## 4. 작업 목표

이번 1차 작업의 세부 목표는 아래와 같다.

1. 문서 기준 패키지 경계를 코드 구조로 먼저 고정한다.
2. 모듈 간 계약이 되는 enum, interface, properties, 기본 모델을 만든다.
3. 외부 시스템과의 연결 없이도 내부 구조를 읽을 수 있는 수준까지 골격을 마련한다.
4. 다음 단계에서 `CallSessionManager`, `SipParser`, `RtpDecoder`, `SttAdapterFactory` 등을 붙일 수 있도록 토대를 만든다.

## 5. 패키지별 범위

### 5.1 common

목적:

- 공통 예외, 상수, 날짜/파일 유틸을 제공한다.

생성 대상:

- `SttgwException`
- `Constants`
- `DateUtils`
- `FileUtils`

제외:

- 도메인 특화 비즈니스 유틸
- 실제 운영 경로 생성/삭제 로직의 고도화

### 5.2 config

목적:

- 향후 설정 바인딩과 공통 빈 구성을 위한 최소한의 기반을 둔다.

생성 대상:

- `AppConfig`

예상 내용:

- `Clock` 빈 제공
- 애플리케이션 전반에서 재사용 가능한 최소 설정만 포함

제외:

- `AsyncConfig`
- `WebSocketConfig`
- `H2Config`

### 5.3 session

목적:

- 통화 세션을 표현하는 기본 상태와 이벤트 계약을 정의한다.

생성 대상:

- `CallState`
- `SessionEventListener`
- `CallSession`

예상 내용:

- 통화 상태 enum
- 세션 생명주기 이벤트 인터페이스
- SSRC 기반 RX/TX 버퍼 누적 구조

제외:

- `CallSessionManager`
- 세션 저장소, DB 저장, 포트 매핑

### 5.4 audio

목적:

- PCM 누적과 오디오 설정의 기반 타입을 만든다.

생성 대상:

- `PcmBuffer`
- `AudioProperties`

예상 내용:

- 스레드 안전한 PCM 청크 누적
- 경로/보존기간 설정 바인딩

제외:

- `WavFileWriter`
- `AudioFileService`

### 5.5 sip

목적:

- SIP 파싱 결과를 담는 타입과 메서드 구분 enum을 만든다.

생성 대상:

- `SipMethodType`
- `SipMessage`

제외:

- `SipParser`

### 5.6 rtp

목적:

- RTP 패킷 구조와 G.711 디코딩의 최소 골격을 마련한다.

생성 대상:

- `RtpPacket`
- `G711Codec`

예상 내용:

- RTP 헤더 파싱
- A-law / u-law 를 PCM 으로 변환하는 기본 메서드

제외:

- `RtpDecoder`

### 5.7 stt

목적:

- STT 벤더 연동을 위한 공통 계약을 먼저 정의한다.

생성 대상:

- `SttMode`
- `SttResult`
- `SttResultCallback`
- `SttStreamingSession`
- `SttAdapter`
- `SttProperties`

제외:

- `SttAdapterFactory`
- `GoogleSttAdapter`
- `GoogleSttProperties`

## 6. 구현 원칙

### 6.1 아키텍처 원칙

- 패키지 경계를 문서 기준으로 분리한다.
- 벤더 의존 타입은 `stt` 인터페이스 바깥으로 새지 않게 한다.
- 세션 이벤트는 `SessionEventListener` 계약으로만 연동되게 설계한다.

### 6.2 코딩 원칙

- 생성자 주입만 사용한다.
- 설정은 `@ConfigurationProperties` 로 바인딩한다.
- `System.out.println` 을 사용하지 않는다.
- 민감 정보 처리와 운영 안정성을 우선한다.
- 실제로 구현하지 않은 동작은 stub 처럼 보이더라도 오해를 줄이도록 이름을 명확히 둔다.

### 6.3 범위 통제 원칙

- 1차에서는 골격만 만든다.
- 동작 서비스 구현과 외부 연동은 다음 단계로 넘긴다.
- 테스트와 빌드는 별도 승인 없이는 수행하지 않는다.

## 8. 예상 리스크

### 8.1 문서와 실제 구현 예시 차이

- `ARCHITECTURE.md` 의 예시 코드는 설명 목적이므로 그대로 복사하면 현재 의존성과 맞지 않을 수 있다.
- 따라서 이번 단계에서는 설명 예시를 그대로 완성 구현으로 옮기지 않고, 현재 프로젝트 상태에 맞는 최소 골격으로 조정한다.

### 8.2 조기 구현 과다

- `CallSessionManager`, `SipParser`, `RtpDecoder` 까지 무리하게 같이 만들면 책임이 섞일 수 있다.
- 이번 단계에서는 타입 계약을 먼저 굳히고 서비스 구현은 다음 단계로 분리한다.

### 8.3 테스트 부재

- 이번 단계에서는 빌드/테스트를 실행하지 않으므로 컴파일 보장은 선언하지 않는다.
- 따라서 코드 작성 시 문법적 일관성과 의존성 적합성을 최대한 보수적으로 유지해야 한다.

## 9. 완료 기준

아래 조건을 만족하면 1차 작업을 완료로 본다.

1. `docs/1차-작업계획서.md` 가 작성되어 있다.
2. 1차 대상 패키지들이 문서 기준 이름으로 생성되어 있다.
3. 각 패키지에 최소 1개 이상의 의미 있는 핵심 타입이 존재한다.
4. `stt` 패키지에 공통 계약 인터페이스와 결과 타입이 존재한다.
5. 작업 단위별 한국어 커밋 메시지로 커밋되어 있다.
6. 각 의미 있는 작업단위 종료 후 GitHub 원격에 푸시되어 있다.
