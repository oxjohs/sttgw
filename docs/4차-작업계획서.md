# 4차 작업계획서

## 1. 목적

본 문서는 `sttgw` 프로젝트의 4차 작업 범위와 구현 원칙을 정의한다.  
4차의 핵심 목표는 현재까지 구현된 세션, 영속성, STT 계약 계층 위에 REST API 계층을 추가하여 외부 클라이언트와 대시보드가 사용할 수 있는 HTTP 진입점을 만드는 것이다.

이번 차수에서는 API의 구조와 응답 형식을 먼저 안정화한다.

## 2. 단일 진실 기준

4차 작업은 아래 문서를 기준으로 한다.

- `AGENTS.md`
- `docs/ARCHITECTURE.md`
- `docs/CONVENTIONS.md`
- `docs/SCHEMA.md`
- `docs/DEPLOYMENT.md`
- `docs/1차-작업계획서.md`
- `docs/2차-작업계획서.md`
- `docs/3차-작업계획서.md`

문서와 코드가 충돌하면 문서를 우선한다.

## 3. 현재 상태

- 현재 `api` 패키지는 없다.
- 내부 서비스 계층은 `CallSessionManager`, `SttAdapterFactory`, JPA repository 수준까지 구현되어 있다.
- 문서상 REST API는 활성 통화 조회, 통화 이력 조회, transcript 조회, STT recognize, vendor 조회, STT 설정 조회/변경이 요구된다.
- 현재 STT 어댑터 구현체는 아직 없으므로 일부 엔드포인트는 구조는 제공하되 실제 호출 시 예외 응답이 발생할 수 있다.

## 4. 4차 작업 목표

이번 4차 작업의 세부 목표는 아래와 같다.

1. `api` 패키지와 DTO 구조를 만든다.
2. 활성 통화, 통화 이력, transcript 조회 API를 구현한다.
3. STT vendor 조회와 recognize API를 구현한다.
4. STT 설정 조회/수정 API를 구현한다.
5. 문서 규칙에 맞는 성공/에러 응답 형식을 적용한다.
6. 구현 후 `compileJava` 와 `test` 로 실제 검증한다.

## 5. 작업 범위

### 5.1 컨트롤러

생성 대상:

- `api/CallController`
- `api/SttController`
- `api/SettingController`

역할:

- `/api/calls`
- `/api/stt`
- `/api/settings`

### 5.2 DTO

생성 대상:

- `api/dto/ApiResponse`
- `api/dto/ApiErrorResponse`
- `api/dto/CallInfoResponse`
- `api/dto/CallRecordResponse`
- `api/dto/SttTranscriptResponse`
- `api/dto/SttResultResponse`
- `api/dto/SttVendorConfigResponse`
- `api/dto/SttSettingRequest`

원칙:

- 엔티티를 컨트롤러에서 직접 반환하지 않는다.
- API 응답은 DTO 중심으로 구성한다.

### 5.3 예외 처리

생성 대상:

- `api/ApiExceptionHandler`

원칙:

- `SttgwException` 은 API 에러 형식으로 변환한다.
- 유효성 오류도 API 에러 형식으로 변환한다.
- 일반 예외는 내부 서버 오류 형식으로 변환한다.

## 6. API 상세 범위

### 6.1 CallController

엔드포인트:

- `GET /api/calls/active`
- `GET /api/calls/history`
- `GET /api/calls/{callId}/transcript`

구현 원칙:

- 활성 통화는 `CallSessionManager` 에서 조회한다.
- 통화 이력은 `CallRecordRepository` 에서 페이지 단위로 조회한다.
- transcript 는 `SttTranscriptRepository` 에서 시간순 조회한다.

### 6.2 SttController

엔드포인트:

- `POST /api/stt/recognize`
- `GET /api/stt/vendors`

구현 원칙:

- recognize 는 현재 어댑터 팩토리를 통해 벤더를 선택한다.
- 어댑터가 없거나 사용 불가면 예외 응답을 반환한다.

### 6.3 SettingController

엔드포인트:

- `GET /api/settings/stt`
- `PUT /api/settings/stt`

구현 원칙:

- 설정 조회는 DB에 없으면 `SttVendorConfig.defaultConfig()` 를 사용한다.
- 설정 수정은 기존 설정을 갱신하거나 신규 생성한다.

## 7. 제외 범위

이번 4차에서는 아래 범위를 제외한다.

- `dashboard` 패키지 구현
- `websocket` 패키지 구현
- 실제 STT 벤더 구현
- 인증/인가
- OpenAPI/Swagger 문서
- API 계층 전용 테스트

API 테스트는 후속 차수에서 `MockMvc` 또는 통합 테스트로 다룬다.

## 9. 예상 리스크

### 9.1 STT recognize 엔드포인트의 실제 동작 한계

- 현재 STT 어댑터 구현체가 없으므로 recognize 는 구조는 존재하지만 실제 호출 시 벤더 미지원 예외가 날 수 있다.
- 이는 7차 STT 구현 전까지 허용한다.

### 9.2 응답 형식 고정

- 이번 차수에서 성공/에러 응답 형식을 한 번 고정하면 이후 프론트와 연동이 쉬워지지만, 변경 비용이 생긴다.
- 따라서 문서 기준 형식을 우선 적용한다.

### 9.3 API 테스트 부재

- 이번 차수에서는 API 구현 후 `compileJava` 와 전체 `test` 만 검증한다.
- 컨트롤러 전용 테스트는 후속 차수에서 보강한다.
