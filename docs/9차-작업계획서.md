# 9차 작업계획서

## 1. 목적

현재 운영 환경에서 `sttgw.capture.bpf-filter` 를 `host 211.192.89.43 and udp` 로 제한한 이후, 통화의 `RX` 음성은 저장되지만 `TX` 음성이 누락되는 현상이 발생한다.  
본 차수의 목적은 **운영 트래픽 범위를 통제하면서도 RX/TX 양방향 음성을 안정적으로 수집·저장**하도록 캡처/세션 매핑 전략을 개선하는 것이다.

## 2. 현재 문제 요약

1. 캡처 필터를 단일 호스트 기준으로 강하게 제한하면 실제 미디어 경로 일부가 필터링될 수 있다.
2. SIP 신호(`INVITE/200/ACK/BYE`)는 보이지만 RTP가 양방향으로 동일 조건을 만족하지 않는 구간이 있다.
3. 그 결과 `CallSession` 채널 등록이 `RX` 중심으로 이루어지고 `TX` 버퍼 누락 가능성이 높아진다.

## 3. 원인 가설

1. SIP 시그널링 호스트(`211.192.89.43`)와 실제 RTP 미디어 종단 호스트가 다를 수 있다.
2. 미디어 릴레이/SBC 구간에서 RTP 소스/목적지 IP가 동적으로 변경될 수 있다.
3. 현재는 포트 기반 `portToCallId` 매핑과 단순 RTP 디코딩 경로를 사용하므로, 캡처 범위가 좁아지면 TX 방향을 잃기 쉽다.

## 4. 설계 원칙

1. 운영 안전성 우선: 불필요한 UDP 전체 수집은 피한다.
2. 음성 완전성 보장: RX/TX 동시 수집을 목표로 한다.
3. 단계적 적용: 필터 완화 → SIP/SDP 기반 식별 강화 → 최종 필터 재축소 순으로 진행한다.
4. 롤백 용이성: 설정 기반으로 즉시 이전 정책으로 되돌릴 수 있어야 한다.

## 5. 구현 대안

### 대안 A (단기 안정화, 권장)

`bpf-filter`를 `host 211.192.89.43 and udp` 에서 아래로 완화한다.

`udp and (host 211.192.89.43 or net 211.192.89.0/24)`

장점:
1. 현재 운영 망의 관련 대역 트래픽을 포함해 TX 유실 가능성을 크게 줄인다.
2. 코드 변경 없이 설정만으로 빠르게 복구 가능하다.

단점:
1. 불필요한 UDP가 일부 유입될 수 있다.
2. `RtpDecoder` 경고 로그가 늘어날 수 있다.

### 대안 B (중기, 구조 개선)

SIP/SDP 파싱 결과(`c=IN IP4`, `m=audio`)를 기반으로 통화별 RTP 허용 후보를 동적으로 관리한다.

장점:
1. 통화 관련 RTP만 선택적으로 처리 가능하다.
2. 필터 완화 폭을 줄이면서 RX/TX 정확도를 높일 수 있다.

단점:
1. 구현 복잡도 상승.
2. SDP 변형 케이스 대응 필요.

### 대안 C (장기, 고도화)

초기 캡처는 완화 필터로 수집하되, 애플리케이션 내부에서 RTP 유효성/코덱/세션 상관관계 검증 후 폐기하는 다단계 파이프라인을 구축한다.

장점:
1. 품질/성능/정확도 균형 최적화 가능.
2. 관측 지표 기반 튜닝이 가능하다.

단점:
1. 개발 기간 증가.
2. 운영 모니터링 체계 필요.

## 6. 9차 범위 (이번 차수)

이번 차수는 **대안 A + 최소 보강**으로 한정한다.

1. `application-prod.yaml`의 `sttgw.capture.bpf-filter`를 완화 필터로 변경한다.
2. `RtpDecoder`의 미지원 PT 경고를 레이트 제한 또는 샘플링 로그로 조정한다.
3. RX/TX 오디오 파일 생성 여부를 통화 단위로 점검할 수 있도록 로그 포인트를 강화한다.

## 7. 파일 변경 계획

1. `src/main/resources/application-prod.yaml`
2. `src/main/java/com/oxjohs/sttgw/rtp/RtpDecoder.java`
3. 필요 시 `src/main/java/com/oxjohs/sttgw/session/CallSessionManager.java`
4. 필요 시 관련 테스트 파일

## 8. 검증 계획

### 8.1 사전 검증

1. `./gradlew compileJava`
2. `./gradlew test`
3. `./gradlew build`

### 8.2 서버 검증

1. 새 JAR 업로드 후 재기동
2. 통화 1건 진행
3. 아래 확인:
   1. `/APP_DATA/audio/yyyy/MM/dd/` 에 `_rx.wav`, `_tx.wav` 둘 다 생성
   2. `CALL_RECORD`에 해당 callId 저장
   3. `STT_TRANSCRIPT`에 callId 데이터 저장

### 8.3 수용 기준(Definition of Done)

1. 동일 callId에 대해 RX/TX WAV 파일 모두 존재
2. STT 결과가 DB에 저장됨
3. 운영 로그에서 치명 오류 없음

## 9. 리스크 및 대응

1. 필터 완화로 트래픽 유입 증가
   - 대응: 경고 로그 레이트 제한, 후속 대안 B 진행
2. 특정 구간 코덱 미지원
   - 대응: payload type 관측 후 지원 대상 확장
3. 운영 성능 저하
   - 대응: 캡처 스레드/큐 상태 모니터링 및 튜닝

## 10. 롤백 전략

1. `application-prod.yaml`의 `bpf-filter`를 이전 값(`host 211.192.89.43 and udp`)으로 복원
2. 이전 안정 버전 JAR로 즉시 교체
3. 서비스 재기동 후 통화 1건 재확인

## 11. 다음 차수(10차) 제안

1. SIP/SDP 기반 동적 RTP 허용 테이블 구현 (대안 B)
2. RTP/RTCP/기타 UDP 식별 정확도 향상
3. 운영 지표(세션 수, RTP drop, STT 처리량) 대시보드 노출
